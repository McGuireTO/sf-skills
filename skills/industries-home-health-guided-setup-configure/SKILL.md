# Home Health Guided Setup

> 🔴 **READ FIRST — if the admin asked to set up Home Health but provided NO specifics, your very first message to them MUST be the full intake template from the "First response" section below (the framing note, the "Two ways to do this" options, the example brief, and the grouped list of information needed), rendered to the user in full — not summarized, not paraphrased, not skipped, and before any discovery summary or write. Then STOP and wait for their choice.** Skipping it is a contract violation. (If they DID provide real details, don't wait — see "Info provided" below.)

Guide a Health Cloud admin through the full `HomeHealthSetupPage` guided-setup wizard — **16 groups / 75 steps** end-to-end. Of these, 4 groups / 21 steps are captured verbatim in the platform's own on-disk wizard configuration file that drives the Home Health setup page; the remaining groups (Field Service scheduling, care personnel, work types/skills, patient app, Agentforce, mobile) are downstream steps that live setup runs have shown extend past what's captured on disk today. The full per-step table (all 75 steps, all 16 groups) lives in [`source/references/setup-json-and-labels.md`](source/references/setup-json-and-labels.md). This skill does NOT assume a customer's business data — it discovers real org state first and asks before writing anything that depends on customer choice (see "Data vs Metadata" below).

This skill deliberately does not re-derive the master Home-Health toggle itself. That's already owned by two existing leaf SORs — `health-cloud-revan/HomeHealthSettings` (standard Setup page) and `health-cloud-renegade/HomeHealthSettingsLSC` (Lightning Setup Component variant). Phase 0 as a whole is now delegated to `health-cloud-revan/home-health-guided-setup-enable-org-fsl`, whose own step 3 **delegates to** whichever of the two leaf SORs applies rather than re-authoring the toggle logic inline — a two-level delegation edge instead of a duplicated cascade that would drift from either. **Sequencing, not just ownership, matters here: the master toggle (step 3) is a hard precondition for everything after it in that delegate — it must complete and be read-back-confirmed before step 4 (FSL package install) is attempted, not run alongside or after it.** Confirmed live: calling the leaf SOR's write action (`handleToggleHomeHealth`) and re-reading `getHomeHealthPref` is the real primary mechanism (it drives the full `FieldServiceEnabled → OptimizationServiceAccess → O2EngineEnabled → HomeHealthEnabled → RescheduleAll` cascade) — a bare `IndustriesSettings.enableHomeHealth` Metadata-only flip is strictly the fallback (same caveat as `home-health-guided-setup-enable-org-fsl` step 3 already documents) and should not be reached for first unless the leaf SOR is genuinely unavailable at runtime.

## Session state

Track across the conversation:
- `org_alias` — which org this run targets (confirm explicitly, never assume).
- `current_phase` — which of the 17 phases (0-16, see routing table) we're on.
- `phase_complete[phase_id]` — booleans, so re-entry resumes rather than restarts.
- `pending_manual_confirmations` — manual steps handed to the admin, awaiting their "done" confirmation before the skill proceeds past that phase.
- `discovered_business_data` — any real ServiceResource/ServiceTerritory/WorkType/Skill/OperatingHours values the admin has already provided this session (never re-ask once given; never invent if not given).
- `step_ledger` — the persistent, step-level record of all ~75 steps (each: phase, step ID, status, verification Id/failure-signal, sweep, timestamp). This is the single source of truth for "how many are done / where do I resume" — kept current as each step resolves, so those questions are answered from it directly, without re-scanning the org (see "Progress memory" below).

**Org-Id independence (NON-NEGOTIABLE):** the companion reference docs (`source/references/*.md`) never contain live org values — any record Id, org Id, org alias, or instance hostname is shown only as a generic placeholder (`<…-Id>`, `<reference-org>`, `<target-org>`, `<…-org-instance-url>`), never as an input. Every Id this skill actually writes or compares against MUST be resolved fresh, on the current target org, at runtime (via `describe`, a query-existing-before-create lookup, or a create's own response) — **never** carried over from a reference doc, a prior run, or a different org. The only exceptions are genuine **platform-fixed literals** that are the same on every org by construction — `DeveloperName`s, `CustomNotifTypeName`s, FQNs, enum values (e.g. `HomeHealthDependentVisits`, `HomeHealthPatientNotification`) — those are safe to hardcode because they're names, not Ids, and the platform's own flows look them up by that same fixed name on any org. If a doc shows a literal 15/18-char Id next to a step, treat it exactly like the execution playbook does: "evidence, not an input — a fresh org mints its own."

## Data vs Metadata — the rule that governs every phase below

**Metadata-shaped steps** — fixed platform defaults, no customer business context needed, safe to automate without asking:
- Record Type creation (`HomeHealthSetupPage.CreateRecordType`) — the platform hardcodes `SobjectType=WorkOrder`, `DeveloperName=HomeHealth`, `Name=Home Health` (source: the Home Health shared labels, section `HHRecordType`). Query first for an existing WorkOrder record type with that DeveloperName; if a *different* WorkOrder record type already exists, surface the conflict and ask before creating a duplicate — otherwise create directly.
- Skill / SkillType definitions — structural picklist-like records; the *mechanism* is metadata even though the *names* chosen are data (see below).
- Scheduling Policy creation (Phase 2e) — the wizard's own action creates a fixed-default record (`{namespace}__Scheduling_Policy__c`, not the standard `AppointmentSchedulingPolicy`) with hardcoded field values and a hardcoded work-rule/goal set; nothing about the wizard's own create is a business decision, but it still writes real records, so it's presented to the admin before creating (see "Present-then-create steps" below) rather than fired silently.
- Entity-rename label *suggestions* — the platform's own suggested label text (e.g. ServiceTerritory → "Care Resource Service Region") is a fixed, Salesforce-authored reference table, safe to *show* without asking; whether the admin adopts it is their choice (see Phase "Update Labels" below).

**Data-shaped steps** — depend entirely on the customer's real business — always ask or discover, never invent:
- ServiceResource identities (who are the actual care professionals?)
- Real WorkTypes chosen (what services does this customer actually offer?)
- Operating Hours schedules (what are this customer's actual coverage hours?)
- Real Skill names and which resources hold them
- License/user assignment (which humans get which license?)
- Service Territory names and member assignments

**Present-then-create steps** — a third shape, distinct from both of the above: the write has *some* fields with real fixed platform defaults and *some* fields that are genuine customer decisions in the same create call (e.g. Phase 2f's Bundling Policy: `LimitAmountOfBundleMembers` defaults to 50, but `Name`/`Priority` have no default at all). For these, discover what the admin has already given this session, present the platform's defaults for the rest explicitly, and let the admin confirm or override — only then create. Never silently apply a default without showing it, and never create before the admin has seen the full field list.

Every phase below is tagged `[metadata — automate]`, `[data — ask/discover]`, or `[present-then-create]` (or a mix, noted per-step) so this rule is auditable, not just asserted. Full per-step table: [`source/references/data-vs-metadata-catalog.md`](source/references/data-vs-metadata-catalog.md).

## Execution contract — what happens when the admin says "set up Home Health"

### 🔴 HARD RULE — EVERY PHASE MUST BE EXECUTED (fully exempt: Phases 5 & 6; Phase 7 exempt ONLY for manual steps 1/2/5 — steps 3 & 4 ARE executed)

**On a full "set up Home Health" run, every phase 0–16 — EXCEPT the exempt set — MUST be entered and every one of its steps MUST be actively executed this run. This is non-negotiable and overrides any sequencing/prioritization guidance below.** A phase or step is NEVER allowed to end the run in `⬜ not-started` or silently un-attempted. The three-sweep model, the "pushed later in execution order" language, and the "Phase 13 first, then Phase 11" FSL-wait ordering are about *sequence*, NOT about *whether* a phase runs — they may reorder when a phase executes, they may NEVER drop one. Phase 11 being "pushed later" and then never returned to is the exact failure this rule forbids.

> **The exempt set (precise — Phase 7 is NOT wholly exempt):** Phases **5 and 6** in full, **plus Phase 7's manual flow-wiring steps 1, 2, and 5 only**. **Phase 7 steps 3 (`EnableRescheduleFlowRecentVersionChoice`) and 4 (`CreateCustomNotification`) have documented headless mechanisms and MUST be executed like any other `[metadata — automate]` step** — step 4 in particular is a plain data-API `POST /sobjects/CustomNotificationType` create (fixed `DeveloperName='HomeHealthDependentVisits'`) and must be run + verified every run. Anywhere below that says "except the exempt set," that carve-out is what it means — never read it as "skip all of Phase 7."

For every phase outside the exempt set, and for every step within it (including Phase 7 steps 3 & 4), the run is only allowed to close when that step is in one of these terminal states — each of which requires an actual attempt this run (per "Attempt-first, fail-to-manual" below):
- `✅ done` — executed + verified (record Id / read-back), or discovery showed it already satisfied;
- `🔒 blocked` — the documented mechanism was **actually called this run** and returned a **literal, quoted org-side failure** (licensing/provisioning/feature gate, `NOT_FOUND`, etc.) — never a stale-tag assumption;
- `awaiting-required-data` — a required customer value that has no safe default is genuinely missing (and was asked for);
- `⏸️ deferred-manual` — a true no-API step (this is only how Phases 5 & 6, Phase 7's manual steps 1/2/5, and other genuinely mechanism-less steps end — NOT Phase 7 steps 3 & 4).

"I didn't get to it," "it was sequenced after other work," "a higher-level tracker was focused elsewhere," and "an earlier run's note said it was deferred" are **NOT** acceptable terminal states. Before declaring setup complete you MUST reconcile that every phase 0–16 outside the exempt set — and Phase 7 steps 3 & 4 — has all its steps in one of the four terminal states above; if any is still `not-started` or un-attempted, the run is not complete — go execute it.

**Phases 5 and 6 are the only wholly-exempt phases; Phase 7 is only PARTIALLY exempt.** The exempt work is genuinely mechanism-less (Service Report visual template authoring, FSL nightly-recurrence Setup config, and Phase 7's installed-package flow wiring/activation — steps 1, 2, 5 — for which no API/MDAPI/Tooling path exists). Those are handed off as guided manual steps. **Phase 7 steps 3 (`EnableRescheduleFlowRecentVersionChoice`) and 4 (`CreateCustomNotification`) are NOT exempt** — they have documented headless mechanisms (step 3: the admin-setup-step-action Connect API resource over `/headless/invoke`; step 4: data-API `POST /sobjects/CustomNotificationType`) and must be attempted/executed + verified like any other automatable step, every run.

**Do NOT rely on any prior run's status log to decide what to skip.** Re-establish state from the org (discovery-first) and this document; a prior "deferred" note never exempts a phase from this rule.

### Three-sweep model (sequence only — never a license to drop a phase)

When the admin asks for setup (not a targeted single-phase ask), work in **three sweeps, not one phase-by-phase pass** — this is what lets automation run to completion without ever blocking on a human, while still asking for exactly the data a step genuinely can't proceed without. **The sweeps govern the *order* steps run in, not *whether* a phase runs — per the HARD RULE above, every phase outside the exempt set (and Phase 7 steps 3 & 4) is executed in full regardless of which sweep its steps land in:**

- **Sweep 1 — every `[metadata — automate]` step, across ALL phases, first.**
- **Sweep 2 — every `[data]` / `[present-then-create]` step, once Sweep 1 is done**, split by whether the missing thing is *required* or *optional* for that specific create.
- **Sweep 3 — every true `[manual]` step (no API at all), batched to the very end.**

A phase is not "entered once and finished" — its Sweep-1 steps may complete in the first pass while its Sweep-2/Sweep-3 steps wait for a later pass. The per-phase ledger (below) reflects this: a phase can legitimately show `partial (awaiting: <thing>)` for many turns while its automatable steps are long done. **Phases whose only remaining work is Sweep 2/3 are pushed later in execution order** — a phase that's 100% automatable finishes before a phase that needs a data prompt or a manual hand-off, regardless of their numeric order in the wizard; the 0→16 numbering still governs presentation/ledger order and audit completeness, not raw execution sequence.

1. **Sweep 1 — `[metadata — automate]` → run it, don't ask.** Discover current state first (idempotency), then write if absent. These have no customer-specific input — Record Type, SkillType shape, all four Custom Notifications (fixed DeveloperNames), FSL settings, Billing enablement, pricing/budget scaffolding. Report what was created (with IDs) as you go; never gate these behind a yes/no prompt. If a discovery shows a *conflicting* existing record, surface the conflict and ask — that's the one exception. **Run this sweep to completion across every phase before starting Sweep 2** — including phases numerically later than one still awaiting a data prompt. (This is also why the FSL async install, Phase 0 step 4, never stalls the run: while that recipe/manual-install is pending, Sweep 1 keeps executing every non-FSL-dependent automatable step in every other phase — see the HARD GATE callout and "Prerequisite polling" below for the exact non-dependent step list.)

   **Attempt-first, fail-to-manual (NON-NEGOTIABLE — this is what Sweep 1 actually means for every phase, not just the ones numbered early).** Every step's `[automate]`/`[manual]`/`[blocked]` tag in this document is a **prior from a previous run, not a guarantee for the org in front of you.** Org state drifts — a platform toggle, license, or prerequisite pref that blocked automation on a past run can be on by the time this run executes (and vice versa). So Sweep 1 must **actually call/deploy the mechanism for every step that has one documented in this file — including steps that carry the `[manual]` tag if a headless/API/MDAPI path is described for them anywhere in this doc** — before it is ever added to the end-of-run manual checklist. Concretely: Phase 13 Step 0's four Agentforce platform toggles and Phase 9 step 6's `IndustriesSettings` briefcase-prerequisite prefs are both tagged `[automate]` in this document and both have a fully-specified MDAPI mechanism below — steps like these must be attempted this run (per their discovery-then-write sequence) and never left un-attempted just because a higher-level tracker sequences them after other work. The correct sequence for **every** step, every run:
   1. **Discover first, every time, before attempting to enable/create anything — never write blind.** Before calling the mechanism, run that step's own documented discovery/read check (a describe, a Tooling query, a `getPreference`/`getInitialStates`-style read, an existence query for the target record) to find out whether the toggle is already on, the record already exists, or the org is already in the target state. This is not optional and not a one-time thing done at session start — it happens **per step, immediately before that step's write**, because org state can have changed since any earlier discovery pass (including one earlier in the very same run, if a different phase's write happened to touch the same preference/object). Only if discovery shows the step is NOT already satisfied do you proceed to try the write. If discovery shows it's already satisfied, mark it `done` from the read alone — never re-run a write "just to be sure" and never treat an already-satisfied step as needing "enabling" again.
   2. **Try the documented mechanism** (headless controller call, Tooling REST, or MDAPI Settings/metadata deploy — whichever this doc specifies for that step) — only when step 1's discovery showed it's genuinely missing. Do not skip a step just because it sits in a phase numbered later than whatever the human or a higher-level tracker is currently focused on.
   3. **If it succeeds** (or discovery in step 1 already showed it's satisfied) → mark that step `done` in the ledger with the record Id/verification, and move on. Never re-litigate a done step.
   4. **If the attempt concretely fails** — a real error, not a guess — **capture the exact failure signal** (`NOT_FOUND` on an object describe, an org-preference gate, a licensing/entitlement gap, a "Legal Terms acceptance" 400, a dispatcher 404, etc.) and **only then** queue it to `pending_manual_confirmations` as a manual/blocked item, **quoting that literal failure reason** — not a generic "manual" label. A step never lands on the end-of-run manual list on the strength of this document's tag alone; it lands there because an attempt was made this run and it produced a specific, named failure.
   5. **Steps with no mechanism documented anywhere in this file at all** (true `[manual]`, e.g. Service Report template authoring, prompt-template visual authoring) skip steps 1-2 — there is nothing to discover or attempt — and go straight to the manual queue, labeled "no API/mechanism exists for this step" so it's visibly distinct from an attempted-and-blocked item.
   6. **When a step documents MORE THAN ONE mechanism, exhaust the org-domain / token-only one before declaring the step blocked — and never let a wrong-mechanism artifact masquerade as a real org boundary.** Some steps offer a convenience path that leaves the org (an external gateway, a differently-prefixed endpoint, a CLI that bootstraps its own auth) *and* a first-class path that stays on the org's own My Domain with the session token. A failure from the off-org path is **not** evidence the org can't do the thing. Concretely, before queueing a step to manual, sort its failure into one of two buckets and **quote which**:
      - **Wrong-mechanism artifact (keep trying) —** a `404`/`NOT_FOUND`/`AgentApiNotFound` from an external gateway or a `/connect`-vs-no-`/connect` prefix mistake, an auth-shape mismatch, a CLI that targets a public gateway the org isn't registered on. These prove nothing about org capability; switch to the org-domain REST path and retry. (Lesson from Phase 13: `sf agent publish` 404s on the external SFAP gateway for orgs not registered on it, but the `POST /nextgen-authoring/bundles` → PATCH → publish chain on the org's own domain runs token-only — reaching a *different*, real response.)
      - **True org boundary (queue to manual, quote it) —** an org-side status like `INSUFFICIENT_ACCESS`, a licensing/entitlement gap, an `OrgProvisioning` fatal, a "Legal Terms" 400, a `501`/`500` on an unprovisioned feature. These are real; queue them with the literal code AND a one-line corroborating signal (e.g. "`OrgProvisioning statusCode:216 Failed Org Status Check Fatal Error` on `CreateContactCenter` → AWS-side SCV provisioning not done — license present but org not provisioned"). Corroborate an entitlement/provisioning guess with a second read whenever one is cheap, so the manual note says *why* it's a real boundary, not just *that* a call failed. **But first rule out a self-inflicted cause:** an `INSUFFICIENT_ACCESS`/`INVALID_API_INPUT` can come from *your own* wrong request shape, not an org limit — Phase 13's publish `INSUFFICIENT_ACCESS`/`EinsteinServiceAgent` errors were caused by building the wrong *agent type*, not by any missing entitlement or the `enableBots`/legal-terms gate. Don't label an access/validation error a "true org boundary" until you've confirmed the request itself was correct.

2. **Sweep 2 — `[data — ask/discover]` → once Sweep 1 is done, split required vs. optional, following the `sfs-sobject-create` pattern.** These need the customer's real business data (ServiceResources, WorkTypes, Operating Hours, Territories, Skills, license/profile assignment, per-WorkType pricing, etc.). Governing rules:

   **(a) Proceed with whatever the admin already gave you — never block a whole step on one missing value.** Use `discovered_business_data` first; only what's genuinely still missing gets flagged, and only per the required/optional split below.

   **(b) Required-but-missing, and no safe default exists → prompt inline, right when that step executes (not deferred).** If a value is required for the create to succeed at all (derived via the describe rule in (d), or the entity itself — e.g. no WorkTypes named at all) — and there is no platform-recommended default a reasonable admin would accept — and it's still missing once Sweep 1 has completed, **stop at that step and ask the admin then and there** — a short, focused, structured prompt (ask/why/impact) for exactly that value. Don't silently invent a placeholder, and don't hold the question until the end of the run; the step cannot execute without it, so ask now, get the answer, then create. The ledger shows `partial (awaiting: <entity> field)` until answered.

   **(b2) Required-but-missing, but a documented skill-known default exists → apply the default and complete the step, don't block on an ask.** Several steps in this skill carry an explicit, named "if unspecified, do X" recommendation elsewhere in this doc (e.g. Phase 13 step 4's agent creation defaults to the shipped `HH Next Scheduler` template with an auto-generated bundle name when the admin hasn't said "build a custom agent" or named an existing one to attach to; the Experience Site template defaults to `Build Your Own (LWR)` when no template preference is given). For these, **apply the documented default, create/proceed, and disclose what was auto-selected and why** ("no agent template specified, so I used the shipped `HH Next Scheduler` template — say so if you'd rather build a custom one") — this is NOT the same as inventing a placeholder value (the default is a real, pre-vetted platform recommendation, not a guess), and it is NOT deferred to end-of-run since the phase can fully complete now. Only fall back to (b)'s blocking ask when the step has no such documented default (e.g. WorkType names, Skill names, territory names — there is no sensible default business name to invent).

   **(c) Optional-but-missing → don't ask, don't block; create with what you have and queue a follow-up for the end.** If a value is optional for the create (the record can be written validly without it — e.g. a WorkType exists but its price wasn't given, or a descriptive field with no downstream dependency), **create the record now using only the required fields**, then add the gap to `pending_manual_confirmations` as an end-of-run item (e.g. "`<WorkType>` — pricing not supplied, `PricebookEntry` pending"). Never prompt mid-run for something optional; it's surfaced once, in the batched end-of-run checklist, alongside every other deferred item.

   **(d) When you DO create, follow the `sfs-sobject-create` pattern exactly** (`delegates_to: sfs-setup-experience/sfs-sobject-create`) — do not hand-roll a different create flow or hardcode a field list:
   - **Check `discovered_business_data` first** — if the admin already gave the relevant context this session (e.g. "our work types are wound care and IV therapy"), use it; do **not** re-ask.
   - **Describe the sObject** (`GET /sobjects/<S>/describe`) and derive the required fields from the rule `createable:true` + `nillable:false` + `defaultedOnCreate:false` — this is the mechanical source of truth for the required/optional split in (b)/(c); never assume field names or prompt for a field the platform defaults.
   - **Query existing records** (`SELECT <required + picklist fields> FROM <S> ORDER BY CreatedDate DESC LIMIT 20`) to learn naming/value conventions, catch duplicates, and confirm write access before spending a create — if the records already exist live, use/confirm/reactivate them rather than re-creating.
   - **Create** — single record via `POST /sobjects/<S>`; related-record DAGs (e.g. `OperatingHours → ServiceTerritory + TimeSlot`, `Skill + WorkType → SkillRequirement`) via `/composite/graph`, topo-sorted with dependency references in one transaction. `201` = success; act on any `errorCode`/`message` rather than blindly retrying (a `400`/`403` is usually a CRUD/FLS gap, not a payload bug).
   - Example: WorkTypes — if the admin never stated which services they offer and none exist on the org, ask "What work types (services) does this customer offer?" only after Sweep 1 is done (required — the entity can't be created blind), then describe→query→create per the pattern above. Contrast pricing on those same WorkTypes: missing price is optional-at-create, so it does NOT block the WorkType/Product/ProductRequired create — only the `PricebookEntry` is skipped and queued per (c).

3. **`[present-then-create]` and every data write → show, then proceed.** Before any create call for customer data (and for present-then-create steps, before applying platform defaults), show the admin the exact records + field values you're about to write, then create. This is not a blocking approval gate on automated metadata steps — but for anything carrying customer data or a defaultable field, the admin sees the payload before it's written, and you proceed once shown (pausing for an explicit override only if they raise one). After writing, read back and confirm.

4. **Sweep 3 — true `[manual]` steps (no API at all) → batch to the very end, and say plainly that the step must be done manually.** Every hand-off in `pending_manual_confirmations` for a genuinely manual step states, in the message itself, that this specific step has no API and must be executed by the admin directly in the Salesforce UI — never phrase it ambiguously as "pending" without saying who has to act. See "Manual steps → batch at the end" below for the full hand-off shape (org-specific link, click-by-click instructions, help doc).

**In one line:** every automatable step across every phase runs first; a data step missing something *required* stops and asks right there; a data step missing something merely *optional* proceeds and queues the gap for the end; and every step with no API at all is batched into one explicit "you must do this manually" checklist at the close. Track everything given/created in `discovered_business_data` so a resumed run never re-asks.

### Mandatory in-order audit + per-phase ledger (NON-NEGOTIABLE — do NOT lose track of a phase)

The per-phase ledger is walked and **presented** strictly in order, 0 → 16, every time it's re-emitted — that ordering is for *auditability*, so the admin can always see where every phase stands. **Execution order is different, by design**: per the three-sweep contract above, Sweep 1 (automate) runs across every phase before Sweep 2 (data-gated) starts on any phase, and phases whose only remaining work is a data prompt or a manual hand-off are pushed later in the run than phases that are fully automatable — even if their phase number is lower. The failure mode the *ledger* prevents: jumping from Phase 7 to Phase 11 (Budget) and reporting "Budget done" while Phase 4 is still silently missing its SkillType/SkillRequirement and Phases 5, 6, 8, 9, 10 have never been touched — an admin reasonably assumes everything before it was done too. The ledger exists to make that impossible, not to force phases to execute in numeric lockstep.

To make silently losing a phase structurally impossible:

1. **Maintain a live per-phase ledger** and re-emit it every time you pause for input or finish a phase. One row per phase 0–16, each tagged exactly one of:
   - `✅ done` — every automatable step in the phase completed + verified; any manual steps in it are recorded in the manual queue (below).
   - `⚠️ partial` — some steps done, others still outstanding. **List the outstanding step IDs explicitly** (e.g. "P4: SkillType, SkillRequirement not created") and whether each is awaiting a *required* prompt (Sweep 2b) or just carries a queued optional gap (Sweep 2c). Never report a phase as done when it's partial.
   - `⏸️ deferred-manual` — the phase's remaining work is manual-only (Sweep 3); steps are in the manual queue for the end.
   - `🔒 blocked` — the step's mechanism was **actually attempted this run** and hit an unmet prerequisite (license/provisioning/org feature); name the blocker with its **literal error/signal**, not a paraphrase (see "Attempt-first, fail-to-manual" above — a phase never gets this tag on the strength of a stale `[manual]` tag alone).
   - `⬜ not-started`.
2. **Report in order, execute by sweep.** The ledger is always *presented* 0→16. Execution does not wait for phase N−1 to close before starting phase N's Sweep-1 work — Sweep 1 runs across all phases concurrently in effect. What IS enforced: never advance a phase to `✅ done` while it has an unresolved *required* Sweep-2 prompt outstanding, and always show a `partial`/`blocked` phase as such rather than letting it look finished. If Sweep 2's required prompt for phase N blocks that phase, keep running Sweep 1 (and Sweep 2 for other phases) rather than idling.
3. **Never silently skip a step OR a phase.** Every step in every phase is either executed, queued as optional-follow-up, queued as manual, or explicitly reported as blocked/awaiting-required-input. There is no fifth "just didn't do it" outcome. Before declaring setup complete, reconcile **at the phase level first, then the step level**: (a) every phase 0–16 **outside the exempt set** must be `✅ done` or, if any step in it is legitimately blocked/awaiting-data, `⚠️ partial` **with each outstanding step named and each carrying a literal attempted-this-run signal** — no phase in this set may be `⬜ not-started` (per the 🔴 HARD RULE at the top of this contract); **Phase 7 is `⚠️ partial` at best — its steps 3 & 4 must be `✅ done`/`🔒 blocked` (attempted this run), and only its steps 1/2/5 sit at `⏸️ deferred-manual`; Phases 5 & 6 are fully `⏸️ deferred-manual`**; and (b) every one of the ~75 steps must then map to done / optional-queued / manual-queued / blocked / awaiting-required-data. A phase sitting at `⬜ not-started` at reconcile time is a contract violation — go execute it before closing.

### Progress memory — answer "how many done / where do I resume" from state, NOT a re-scan (NON-NEGOTIABLE)

Every run maintains the live, step-level `step_ledger` (see Session state) and **updates it the moment each step resolves** — one entry per step across all ~75 steps, each carrying: phase, step ID, one status (`done` / `partial` / `blocked` / `deferred-manual` / `awaiting-required-data` / `not-started`), the verification detail (record Id created, or the literal failure signal), and which sweep it belongs to. Persist it durably (write it to the run's state file / artifact, keyed by `org_alias`) so it survives context compaction and turn boundaries within the run.

Because this ledger is kept current as work happens, when the admin asks **"how many steps are done?"**, **"what's left?"**, or **"where do I resume?"** at any point, answer **directly from `step_ledger`** — a count plus the next incomplete step — **without re-querying the org**. Re-scanning the org is reserved for exactly two cases: (1) a fresh session re-entry (the "Discovery-first re-entry" path, where prior in-memory state is gone), or (2) the admin explicitly asks to re-verify against the org. Never make the admin sit through a full org re-discovery just to be told a count you already hold.

### Manual steps → batch at the end (do NOT block mid-run, do NOT silently skip, and NEVER queue a step as manual without first attempting it)

A step reaches the end-of-run manual checklist through exactly one of two doors — and every item in the checklist must say which door it came through, because they carry different weight for the admin:

- **Door 1 — attempted this run, concretely failed.** This is every step tagged `[automate]`/`[metadata]`/`[automate-the-mechanism]` anywhere in this doc, including ones a past run's blocker note might make you assume are hopeless. Per "Attempt-first, fail-to-manual" above, you called the documented mechanism, and it returned a specific, real error (org-preference gate, `NOT_FOUND` describe, licensing/entitlement absence, "Legal Terms acceptance," dispatcher 404, etc.). Record the **literal failure signal**, not a paraphrase — the admin (or the next run) needs the exact error to know when it's resolved.
- **Door 2 — no mechanism exists, full stop.** True `[manual]` steps with zero API/MDAPI/Tooling path documented anywhere in this file (Service Report template authoring, nightly recurrence job config, installed-package flow activation, entity-label rename, visual prompt-template authoring). There's nothing to attempt, so this is stated as "no API/mechanism exists for this step," not as a failure.

Never let a step land in the checklist on the strength of this document's `[manual]` tag alone if a mechanism is actually described for it elsewhere in the doc — that tag can be stale relative to the org in front of you (a toggle/pref/license state can differ run to run). Tag-driven skipping without an attempt is exactly the bug this section exists to prevent.

For every step, regardless of which door it came through, **do not stop and wait** and **do not skip it silently**. Instead:

1. **Record it in a running manual queue** (`pending_manual_confirmations`) the moment you reach it — capture: phase, step ID, what it accomplishes, **which door it came through (attempted-and-failed, with the literal error / vs. no-mechanism-exists)**, the exact org-specific link, click-by-click instructions, and the public help-doc link. **State explicitly, in the item itself, that this step has no API and the admin must execute it manually** — don't leave that implicit.
2. **Keep going** — continue auto-running every automatable step in this and later phases; the manual step does not block them unless a later automatable step has a hard data/state dependency on it (if so, mark that dependent step `awaiting: <manual step>` in the ledger).
3. **At the very end of the run, present the consolidated manual checklist** — the full `pending_manual_confirmations` queue as one ordered hand-off list, grouped by kind: **(a) attempted, blocked by a real error** (each with its literal failure signal — e.g. `"Legal Terms acceptance and/or necessary feature dependencies required"`, or `Quote sObject NOT_FOUND`), **(b) no mechanism exists at all** (true `[manual]`), and **(c) optional data gaps** (pricing/etc. not supplied) — so the admin does all remaining work in one sitting and can tell at a glance which items are "click accept and I'm done" vs. "genuinely needs Setup UI work" vs. "just needs you to give me a value." Then offer to verify each once they report back.

This is the opposite of blocking per-step: automatable work never waits on a human, but no manual step (and no optional data gap) is ever lost — it's all collected and handed off together at the close, and every item's presence in that list is backed by an actual attempt this run, not an assumption carried over from a prior one.

### End-of-run summary — present FOUR lists, in list form (not a table)

At the close of every run (and whenever the admin asks "what's the final status"), present the outcome as **four explicit lists**, in this order — plain bulleted lists, **not** a table:

1. **✅ Completed** — every step actually done and verified this run, each with its record Id / confirmation. Pull straight from `step_ledger` (status `done`).
2. **🟡 Doable headlessly the moment you answer — needs data only** — steps that have a working, proven headless mechanism and are **not** blocked by any missing API/prerequisite; the *only* thing keeping them incomplete is a required customer value that wasn't supplied (or the admin chose "later"). **List ONLY steps that are still incomplete AND gated purely on data** (ledger status `awaiting-required-data`, plus the optional-gap items from `pending_manual_confirmations` group (c)); a step already `done`, or one blocked on anything other than data, never appears here. For **each** item name it by **its readable step name, not just the phase number** — write it as `Phase <n> — <human-readable step name> (<StepId>)` (e.g. `Phase 9 — Set up mobile object permissions (SetupMobileEntityAccess)`, `Phase 11 — Assign record types to profiles (AssignBudgetRecordTypeToProfile)`), so the admin can tell at a glance *which* step it is without cross-referencing — then state three things: **(a)** the exact missing input(s), **(b)** what completing it unblocks, and **(c)** an explicit standing offer — *"give me this value and I will execute this step headlessly in this same run; it does NOT require any manual UI work from you."* **These are emphatically NOT manual steps** — do not let them read as part of list 4. 3. **⛔ Not doable here — no mechanism / hard-blocked** — steps with no API/MDAPI/Tooling path at all (Door 2), plus steps attempted this run that hit an unmet prerequisite (Door 1) — each with its **literal failure signal**, or "no API exists for this step."

## Manual steps + prerequisite polling — never leave the admin stuck

Many phases have steps with no API (managed-package install, entity-label rename, installed-package flow activation, visual template/prompt authoring). These are **guided manual hand-offs**, not dead ends — the skill's job is to walk the admin through each one and then pick the run back up automatically. Apply this loop to every `[manual]` step and every blocked prerequisite:

1. **Guide, don't just name it.** Present the step with: (a) what it accomplishes and why it's needed, (b) the **exact org-specific link** to the right Setup/Builder page, (c) numbered click-by-click instructions, (d) the public help-doc link. Never assume the admin knows the navigation — spell it out.
2. **State what's blocked behind it.** Tell the admin which later steps can't complete until this manual step is done, and which steps you *can* keep doing in parallel meanwhile (so progress never fully stalls on a manual hand-off).
3. **Wait for the admin's "done" signal**, then **verify, don't trust.** Re-run the step's discovery check (e.g. the FSL Tooling query, a flow's `ActiveVersionId`, a package namespace probe) to confirm it actually landed. If the check still fails, tell the admin exactly what you looked for and what you found, and keep waiting — don't advance on an unverified claim.
4. **On verified success, resume automatically.** Immediately continue with the now-unblocked steps and everything downstream, without making the admin re-issue the "set up Home Health" ask. Update `discovered_business_data` so the resumed flow doesn't re-do or re-ask completed work.

**Prerequisite polling (the FSL install pattern, generalized).** When a hard prerequisite is unmet (FSL package absent, a required org feature un-provisioned), after handing off the manual instructions **re-check the prerequisite each time the admin responds** — treat any admin message during the wait as a possible "is it ready?" and re-run the discovery probe. When it flips to satisfied, announce it ("✅ Field Service package detected — resuming setup") and proceed through the blocked steps in dependency order. Do **not** silently poll on a timer or fabricate a "still waiting" status; the check happens on each admin turn, and the result (installed / still-not-installed, with the exact query result) is reported back plainly. While waiting, keep running any non-blocked automatable steps and report those results as they complete, so the admin sees continuous progress rather than a hard stop.

1. `AssignQuickAction` — `[automate — headless Metadata REST deploy]`. Places the **Patient Details** action (`WorkOrder._PatientDetails`) on **EVERY Work Order page layout** (customer requirement — not just the default; all WO layouts must carry it so every persona sees it). The action appears in the layout's **"Salesforce Mobile and Lightning Experience Actions" section = `platformActionList`**, NOT `quickActionList`. **Verified against a reference org:** `WorkOrder._PatientDetails` is present in `platformActionList` on **both** of the reference org's Work Order layouts (it's not always at index 0 — on the FSL layout `WorkOrder_Omni` leads; read the whole list, don't just check position 0). `_PatientDetails` is a **standard/mobile platform action** with **no `QuickActionDefinition` record** (the reference org has 40 QADs, none named PatientDetails) — it can only be referenced via `platformActionList`.

Returns `201` + a deploy id; poll `GET /metadata/deployRequest/<id>?includeDetails=true` until `deployResult.done`. (NOTE: the deploy body is **multipart**, NOT a JSON `{"file":<b64>}` body — that 400s `Unrecognized field "file"`.)

You MUST build a **full override**: prepend `{"actionName":"WorkOrder._PatientDetails","actionType":"QuickAction","sortOrder":0}` to the layout's **own existing `quickActionList` actions** (renumber the rest), giving ~12 items. **Do NOT copy the reference org's full PAL verbatim** — ref carries custom actions (`WorkOrder.WorkOrder_Omni`, `WorkOrder.Upload_file`) that don't exist on a fresh org and deploy-fail `"no QuickAction named WorkOrder.WorkOrder_Omni found"`. **Validate every action name against the target first** via `GET /sobjects/WorkOrder/quickActions` (returns the resolvable actions; confirm `WorkOrder._PatientDetails` is present — it ships with the HH/FSL package as a `LightningWebComponent` action labeled "Patient Details"). Idempotent: skip layouts that already contain `_PatientDetails`.
   - ⚠️ **CRITICAL GOTCHA #2 — a standard screen action needs a `<subtype>` on FIRST introduction, or it silently never renders** (cross-checked against the `add-platform-actions-to-layout` reference SOR). `WorkOrder._PatientDetails` is an LWC-backed standard screen action, so its `platformActionListItems` block MUST carry `<subtype>LightningWebComponent_ScreenAction</subtype>` (after `<sortOrder>`) the first time it is added to a layout. Without it the deploy still returns `Succeeded` **and** the item round-trips in the layout XML — but the action never binds at runtime and never appears on the record page. This is a **distinct** failure from the single-item-list gotcha above: a full 12-item override can still fail to render if the `_PatientDetails` item lacks `<subtype>`. Two subtleties: (a) MDAPI **retrieve strips `<subtype>` from its response**, so a read-back showing `subtype:null` proves nothing — you cannot detect a missing binding from any read route; the runtime detector (the actions-from-page-layout lookup) is the only cross-check, and it is unavailable on orgs where the Aura-controller proxy is unwired. (b) The subtype value is **not discoverable on the org** — source it from the action's core registration (`LayoutUtil`: `_PatientDetails` → `QuickActionType.LightningWebComponent` → `LightningWebComponent_ScreenAction`; the Aura variant would be `Aura_ScreenAction`). **Because you cannot verify the binding by reading, always deploy the `<subtype>` explicitly on any (re-)deploy** — it is a harmless no-op if already bound and the fix if not. Pre-existing entity-qualified items already present keep their binding on redeploy without re-attaching subtype; standard global QAs (`NewTask`, `LogACall`) and custom QAs never need it.
   - **Expected result:** deploy to **all** WO layouts on the target (e.g. `Field Service Dispatcher/Technician/System Administrator Work Order Layout`, `WorkOrder-FSL__Work Order Layout`, `WorkOrder-Work Order Layout`) in one multipart deploy → `Succeeded, N deployed, 0 errors`; read-back should confirm a full action list with `_PatientDetails` at sortOrder 0 on every one. Standing change (persistent). UI note: hard-refresh the layout editor (setup UI caches action lists). 6. `SetupBriefcase` — **create BOTH briefcases; they are two halves of one step, not an either/or.** Org link: `/lightning/setup/Briefcase/home`; help doc: https://sfdc.co/HomeHealthBriefcase. A complete Home Health mobile setup ships **both** the single-rule Appointments briefcase **and** the multi-rule offline Assessments briefcase — do not stop after the Appointments one. The offline Assessments briefcase depends on a feature gate (see below), so **whenever you enable the briefcase step, enable the offline Assessments feature + briefcase in the same pass** — never leave it half-done with only Appointments created (a state where Appointments lands but offline Assessments is silently skipped because the feature-enable path was unavailable is the exact failure to avoid). The two sub-sections below are split by rule count only for the mechanism detail — both are in scope on every run.
   - **Single-rule briefcase (Home Health Appointments) — `[automate]`.** Created via **Metadata API `BriefcaseDefinition` deploy** (`briefcaseDefinitions/<name>.briefcaseDefinition-meta.xml`), targeting ServiceAppointment, recordLimit 500, `SchedStartTime ≥ TODAY`.
     - **Two shape traps (both cause an opaque `500 UNKNOWN_EXCEPTION` on a Tooling-API create, which is why MDAPI deploy is the recommended path — it returns the *real* parse error):**
       1. **`filterOperator` is a single lowercase char, NOT a word.** The `BriefcaseFilterOperator` enum literals are: `e`(=), `n`(≠), `l`(<), `g`(>), `m`(≤), `h`(≥), `s`(Starts with), `d`(Ends with). Sending `greaterOrEqual`/`lessOrEqual` fails `not a valid value for the enum 'BriefcaseFilterOperator'`. So `SchedStartTime ≥ TODAY` → operator `h`.
       2. **`targetEntityField` is the BARE field name, NOT object-prefixed.** Use `SchedStartTime`, not `ServiceAppointment.SchedStartTime` — the prefixed form fails `Required fields are missing: [TargetEntityField]` (a misleading message; the field is present but the value is rejected). The `targetEntity` element carries the object; the field must not repeat it.
     - Metadata element order (strict): `briefcaseRules` (each: `briefcaseRuleFilters` → `filterLogic` → `recordLimit` → `targetEntity`) → `description` → `isActive` → `masterLabel`.          - `{pref:"AssessmentPref", value:true}` → 200, flips `enableIndustriesAssessment=true`.
         - `{pref:"NextGenDFPref", value:true}` (alias `"DiscoveryFrameworkMetadata"`) → 200, flips `enableDiscoveryFrameworkMetadata=true`.

         <IndustriesSettings xmlns="http://soap.sforce.com/2006/04/metadata">
             <enableIndustriesAssessment>true</enableIndustriesAssessment>
             <enableDiscoveryFrameworkMetadata>true</enableDiscoveryFrameworkMetadata>

         Settings deploys **merge** (unlisted prefs are untouched), so a two-flag file is safe. `sf project deploy start --metadata-dir <dir>` → `Succeeded`.
       - **Still DO NOT PATCH `IndustriesSettings` via Tooling directly** — Tooling `sobjects/IndustriesSettings` PATCH rejects even a no-op (`JSON_PARSER_ERROR: Cannot deserialize instance of complexvalue from VALUE_TRUE` — the flags read as scalar booleans but the write schema types them as complexvalue).
       - After either path, `sobjects/Assessment/describe` returns 200 and the Assessment object tree exists.

**Four deploy gotchas — all are hard requirements, not style:**
- **Deploy at API v68.0 or higher.** `showPatientCard` is a `minAPI="68"` property on `homeHealthPatientVisitTab` (the collapsible inline patient card that replaces the removed sidebar Flexcard). At v62 the deploy fails `Invalidnull property [showPatientCard] in component [healthcloud:homeHealthPatientVisitTab]`; at v68 it validates and deploys. Set `sourceApiVersion`/`--api-version` to 68.
- **This is a standalone page (no `parentFlexiPage`) — never add `<mode>` to any region.** Retrieved reference pages that have a `parentFlexiPage` carry `<mode>Replace</mode>` on every region; a standalone page copied with those `<mode>` tags fails deploy (`"region … specifies mode 'REPLACE' but a parent region enabling that mode doesn't exist"`). Strip them.
- **Each `flexipage:tab` `componentInstance` in the `maintabs` facet needs its OWN `<itemInstances>` wrapper — never group multiple `componentInstance` elements under one `<itemInstances>`.** Putting all 8 tab `componentInstance`s inside a single `<itemInstances>` block fails `Error parsing file: Element componentInstance is duplicated at this location in type ItemInstance`. Fix: repeat `<itemInstances><componentInstance>...</componentInstance></itemInstances>` eight times (one per tab), all still inside the same `maintabs` `<flexiPageRegions>` block.
- **`identifier` values on `componentInstance` are alphanumeric + underscore only — no hyphens.** A hand-authored `hhAppointmentRequests-1`-style identifier fails `The Identifier field value '...' is invalid. An identifier can contain only underscores and alphanumeric characters.` Use `hhAppointmentRequests_1` (underscore, not hyphen) for every generated identifier.

**Step B — activate it at TWO levels (this is the part the earlier note got half-right).** There is no `FlexiPageAssignment` metadata type; activation is an `actionOverride`. This is the one that makes the page show for a Person Account inside the HH app; without it, the record falls back to the app's or the classic layout. **Confirmed against the customer's reference org**, whose `standard__HomeHealth` app sets exactly this (its own Account record page via `pageOrSobjectType: Account`).

**On the Budget & Quote tabs (org-access gates, traced in core):** each component self-gates via its `js-meta.xml` `<orgAccess>` — `homeHealthPatientBudgetContainer` → `HealthCloud.orgHasBudgetInHomeHealth`, `homeHealthPatientQuoteTab` → `HealthCloud.orgHasQuoteInHomeHealth`. **Both of those access checks resolve (in `HealthCloud.accessChecks.xml`) to the identical condition `HealthCloud.orgHasHealthCloud && HealthCloud.orgHasHomeHealthEnabled` — the SAME gate as the Visits/Authorization/Preferences tabs that render.** There is **no separate "Budget feature" or "Quote feature" org preference to enable** — do not invent an enablement step for them (that would be fabricating setup data). The tab components deploy successfully whether or not the gate is satisfied (Budget has been observed to deploy clean even though the `Budget`/`BudgetPeriod` objects are absent — object presence is NOT the gate); if a tab renders empty/hidden at runtime it is a user-permission/feature-visibility matter (e.g. the `HomeHealthQuote` user permission, `[data — ask]`), not a page-authoring or deploy problem.

**⚠️ If the WHOLE tab set appears missing when the admin opens an account, check Person Accounts FIRST — this is the single most common "I set up the page but the tabs aren't there" cause.** The `HomeHealthAccountRecordPage` and all its assignment overrides (org-default, HH-app-default, profile overrides) can be perfectly correct in metadata, yet the admin opens a **business account** (e.g. Acme, Global Media) and sees a near-empty page. The HH patient tabs are built for **Person Accounts**; on a business account they don't render. If Person Accounts is disabled entirely (no `Account.IsPersonAccount` field), there are no patient records to open at all. This is the **Person Accounts prerequisite** in Section A — not a page/assignment defect. Diagnose by confirming (a) `Account.IsPersonAccount` exists (Person Accounts enabled) and (b) the record being opened is actually a Person Account, before touching the FlexiPage or its overrides. (Common failure mode: the page is complete with all 8 tabs + every override pointing to it, but Person Accounts is off and the admin is opening business accounts — the tabs appear "missing" purely because of that.)

**Before deploying, show the admin what exists today** — query `FlexiPage` where `EntityDefinitionId=Account` and surface the current Account page(s); this is a potentially customer-customized page, so confirm the reshape (and which org-gated tabs to include) before overwriting.

**⚠️ Render propagation is NOT instant — do not report "done" the instant the deploy Succeeds.** In practice, the FlexiPage deploy + both `actionOverride` deploys can all return `Succeeded` and read back correctly (`View`/`type=Flexipage`/`formFactor=Large`/`content=HomeHealthAccountRecordPage` present on both the Account object and the `standard__HomeHealth` app), yet the admin may still see the OLD page for several minutes. It resolved on its own (cache propagation) + a hard refresh (Cmd+Shift+R). Guidance: after the overrides read back clean, tell the admin the assignment is deployed and to **hard-refresh / reopen the record**, and that it may take a few minutes to propagate — do NOT keep re-deploying (the metadata was already correct) and do NOT claim the render changed until the admin confirms it visually. The metadata `actionOverride` IS the correct, sufficient mechanism (no UI-only activation step is required); the only trap is impatience. Precedence note: with **0 custom Account record types** on the org, the org-default + app-default overrides cover *all* Account pages in the HH app — there is no per-record-type override to add. If an org DOES have Account record types with their own page assignments, add a matching `View`/`type=Flexipage` override per record type (a record-type-scoped assignment outranks the plain default). **When Account record types are present** (e.g. `Account`, `PersonAccount`, `Business_Account`): if neither `Account.object` nor the `standard__HomeHealth` app carries a record-type-scoped `View` override for them, the plain org-default + app-default overrides (both `content=HomeHealthAccountRecordPage`) are what resolve for a real Person Account record (`SELECT ... FROM Account WHERE IsPersonAccount=true`) — so the page renders correctly for Person Accounts **without** needing an additional per-record-type override. Only add one if the org's admin has actually configured distinct page assignments per Account record type (check via retrieved `Account.object` / app metadata before assuming you need to add one).

This activation-override mechanism is distinct from — and does not automate — the wizard's own `AppDefaultLayoutStepName` checkbox (Phase 8), which remains a bare manual "mark as complete" acknowledgment with no config action of its own (confirmed `no_api`). What's automatable is the actual "make this page the default" behavior; the wizard's checkbox is just Home Health's own tracking of whether that was done.

     If there is insufficient information for a part of the readout, omit that segment entirely. Do not guess, and do not say phrases like "no data available."
     Maintain a warm, professional, and confident tone, acting like a trusted colleague briefing you rather than a formal clinical report or a robotic announcer.

State the scheduled date and time as documented; do not assume or imply the visit is happening right now, since this briefing may be listened to well before the visit.
