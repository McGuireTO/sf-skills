**Setting up Referral Management means running all seven acts in order — Act 0 (foundation), Act 1 (turn on Referral Management), Act 2 (internal referral creation & routing), Act 3 (eligibility / prior auth / scoring), Act 4 (outreach + appointment sync), Act 5 (external document intake), and Act 6 (public referral portal).**

Guide an admin through standing up **Health Cloud Referral Management** in the **strict order** the underlying preferences and platform features require, with a validate-only stance on anything genuinely external to Salesforce (Health Cloud license, Person Accounts, MuleSoft, Marketing Cloud, Google reCAPTCHA, Data Cloud kits).

This skill drives the **project-codey MCP** (`discover` → `describe` → `dispatch`) against the target org. Most steps are live-dispatchable: the Referral Management org-preference toggles, Criteria-Based Search & Filter, the guest-referral record owner, appointment sync, reCAPTCHA verification, the Case record type (Tooling `RecordType`), the Business Rules Engine routes (expression set + decision table), and the flow/Apex/OmniScript/Experience-site surfaces. The rest are GAPS — external systems, user-level entitlements the running identity lacks, multipart-only transports `dispatch` can't send, **or Metadata-API types the Core MetadataCrud allowlist rejects (`PathAssistant`, `BusinessProcess`, `NamedCredential` — live-verified `UNSUPPORTED_OPERATION`), which are deployed via the Salesforce-CLI MDAPI fallback (rule 3/3a/5)**. **Surface every gap with its remediation; never fake a call for one.** Gate every write on an independent read-back, never the write's own echo.

## Transport & deploy discipline (applies to EVERY Act — read before your first write)

These rules are cross-cutting.

**Rule 0 — dispatch-first, CLI-fallback, manual last.** The project-codey MCP is the primary transport for EVERY step: first search the catalog (`discover` / `discover` → `describe` → `dispatch`) for a served Connect API or `/headless` operation that performs the step, then dispatch it and gate on an independent read-back. Only when NO served operation exists (a routes gap — search returns nothing / `dispatch` 404s), the dispatch errors, or the read-back shows the change did not stick, fall back to a **Metadata API deploy via the Salesforce CLI** — but only if you have shell access with the CLI resolvable and an authenticated target-org alias; build the minimal metadata source, deploy, and gate on the same read-back. Surface a step as a manual / out-of-band action (citing its Salesforce Help link) only as the LAST resort, when neither the platform nor the CLI can complete it. Never hand the admin a manual step you could have dispatched or deployed; never claim a step done without a read-back. The concrete CLI commands live in the skill's execution-policy notes; the steps that stay manual even WITH CLI access (external systems, managed-content clones, Setup/Experience-Builder-UI-only designers) are called out per Act.

1. **Everything goes through the project-codey MCP.** `discover` (search — try multiple angles / search by controller class / `list_apis` by team before declaring "no API") → `describe` (ALWAYS before any PATCH/POST — you need the full input schema) → `dispatch` (hits the connected org). `implemented` = a real core Connect API; `proposed` = an Aura controller behind the Headless360 dispatcher (`/headless/invoke/...`). Both are first-class.

2. **Prefer the `/headless/invoke/...` Aura toggles for the referral prefs** over any metadata equivalent: `enable-criteria-based-search-and-filter`, `enable-appointment-sync`, `enable-captcha-verification`, and the `owner-id-setup` read+`save-owner` chain each return 200; gate on an independent read-back.

3. **`/services/data/v67.0/headless/metadata` is the xmlRep master transport — but it is backed by a STATIC MetadataCrud allowlist (Core-side `setup-ui-crud-api`), NOT every Metadata-API type.** Body is `{type, fullName, xmlRep}` where `xmlRep` is a **Metadata-API XML string** for the component. **Verb split: POST = create, PUT = update/merge (component-level).** It reaches the types the allowlist covers — verified live for Settings singletons (`type:IndustriesSettings`, GET + PUT) and `type:OmniProcess` (step 35; the schema validator walks required fields one at a time, e.g. `omniProcessType` then `uniqueName`, so probe the 400-chain to complete the body). **A type the allowlist does NOT cover returns `400 UNSUPPORTED_OPERATION "MetadataCrud does not support CREATE/READ on type: <T>"` — this is a hard Core gate, not a body problem.** `PathAssistant` (step 7), `BusinessProcess` (step 13 — even embedded in a parent `CustomObject`; see rule 3a), and `NamedCredential` (step 24) are all UNSUPPORTED for both CREATE and READ (live-verified) — deploy them via the MDAPI CLI fallback (Transport rule 0; same `sf project deploy start --metadata-dir` mechanics as rule 3c), and gate on a Tooling read-back. Use the version-prefixed path; the un-prefixed `/headless/metadata` (Aura-dispatcher) form returns `"No controller mapping"` and is NOT wired.

   3a. **A Case `BusinessProcess` is NOT reachable through `/headless/metadata` at all — deploy it via the MDAPI CLI fallback.** Neither the top-level `type:BusinessProcess` nor embedding it as a `businessProcesses` child of a parent `type:CustomObject` (`fullName:"Case"`) works: Core resolves the child to its own type and returns `400 UNSUPPORTED_OPERATION "MetadataCrud does not support CREATE on type: BusinessProcess"` (live-verified). The Tooling-REST `POST .../tooling/sobjects/BusinessProcess` path also fails (the complexvalue deserializer rejects scalar `Metadata` sub-fields). **The working transport is an MDAPI deploy** (rule 3c mechanics): build a minimal `objects/Case.object` (or a `businessProcesses`-scoped `CustomObject` component) with the `<businessProcesses>` element and deploy via the Salesforce CLI, then gate on a Tooling read-back. **The `<values>` inside the `businessProcesses` MUST be a subset of the target org's LIVE `Case.Status` picklist values — these vary per org, so discover them live (describe / `FieldDefinition`) before building the body; do NOT copy values from this SKILL or the SOR.** A value the org doesn't have fails deploy with `FIELD_INTEGRITY_EXCEPTION "Picklist value: <X> not found"`.

   3b. **The Case record type itself is created via the Tooling `RecordType` sObject** (after its BusinessProcess exists, rule 3a): `POST /services/data/v67.0/tooling/sobjects/RecordType` with `{FullName:'Case.<Name>', Metadata:{label, active, businessProcess:'<BP name>'}}` → 201. A Case RecordType REQUIRES `businessProcess` (400 "businessProcess required" without it) — unlike an **Account** RecordType, which needs none. RecordTypes are `deletable:false` via Tooling — deactivate (`active:false`), never DELETE. Gate on a Tooling `RecordType` read-back (confirm `BusinessProcessId` points to the BP).

   3c. **Standard picklist values on standard entities cannot be added via ANY REST transport — and the parent-CustomObject `valueSet` PUT returns a FALSE-POSITIVE `success:true` that is a SILENT NO-OP.** For CSR `Status`/`StatusReason`, all three transports fail: (a) Tooling `CustomField/ClinicalServiceRequest.Status` PATCH → 404 (standard fields are not `00N…`-addressable); (b) `type:CustomField` inline `valueSet` → `success:false FIELD_INTEGRITY_EXCEPTION "cannot define valueSet on a standard field. Use StandardValueSet instead"`; (c) the rule-3a parent pattern `PUT type=CustomObject` embedding `<fields><fullName>Status</fullName><valueSet>…` returns `success:true` **but the value is NOT added** (describe read-back shows original values unchanged). **Always verify a picklist write with a `describe` read-back — a false-positive success is more dangerous than an honest rejection.** The backing `StandardValueSet` DeveloperNames are **`CServiceRequestStatus`** (CSR `Status`) and **`CServiceRequestStatReason`** (CSR `StatusReason`); direct Tooling `StandardValueSet` PATCH fails (`FIELD_INTEGRITY "Full name must be specified"` / `MALFORMED_ID` / `Unable to load specified entity`; sentinel Id `000000000000000AAA`). **The working transport is an MDAPI `StandardValueSet` deploy:** `POST /services/data/v67.0/metadata/deployRequest` (`multipart/form-data`: JSON `deployOptions` + a zip of `package.xml` + `standardValueSets/<Name>.standardValueSet`). Because that endpoint is `multipart/form-data`, **`dispatch` (JSON body only) cannot send it** — drive the deploy via the Salesforce CLI (concrete `deployRequest` command in the execution-policy notes), a direct multipart HTTP POST to `/metadata/deployRequest`, the Metadata API SOAP endpoint, or the Setup UI picklist editor. Two load-bearing deploy rules: **(1) the deploy REPLACES the full value list, it does NOT merge** — **retrieve the existing `StandardValueSet:CServiceRequestStatus` FIRST** (via the same CLI) to capture the authoritative existing `fullName`s (the shipped FHIR values), then deploy the union (existing + new) or you drop the shipped values; **(2) the stored API `fullName`s use underscores** — `Waiting_for_Response`, `Manual_Review_Needed`, `Closed_No_Appointment` (labels have spaces/hyphens) — so the decision table (steps 16/17) must key on the underscore API values, not the display labels. `add-csr-status-picklist-values` / `add-csr-status-reason-picklist-values` are required content, achievable but out-of-band relative to the JSON-only `dispatch` surface.

Screen/canvas elements REQUIRE `locationX`/`locationY` (else 400 "Required field is missing: locationX"). (See Act 2 — for the packaged referral flows, clone rather than build from scratch.)

   The one hard multipart limit is the CSR `Status`/`StatusReason` picklist adds (steps 18/19 — rule 3c); every other step is reachable through `dispatch`.

   4a. **PRECONDITION — the Business Rules Engine FAMILY must be provisioned on the org, and it CANNOT be self-enabled headlessly.** Steps 16/17 create cleanly *only* when the BRE family is on. Without it, both calls hard-fail with a feature gate: `GET /connect/ruleengine/usage-types` → **403 `FUNCTIONALITY_NOT_ENABLED [BusinessRuleEngineFamily]`** and `POST /connect/business-rules/expression-set` → **403 `FUNCTIONALITY_NOT_ENABLED [InteractionCalculationProcedures]`** (the decision table additionally needs the Decision Table permission).    Once provisioned: `POST /connect/business-rules/expression-set` requires `usageType`, which MUST be a value from `GET /connect/ruleengine/usage-types` — **`Bre`** (label "Default") is the general-purpose type; free-text guesses ("Decisioning") 400 "Value does not match expected type". `POST /connect/business-rules/decision-table/definitions` needs BOTH `dataSpaceName` AND a `parameters[]` array (absent `parameters` → 500 NPE); `parameters[].dataType` ∈ `{Boolean,Currency,Date,DateTime,Number,Percent,String}` (**not** "Text"); `usage` ∈ `{Input,Output,RowCriteria}`; **Output fields must NOT carry a `sequence`** ("You can't specify the sequence number for output fields"); needs the Decision Table permission. Do NOT switch to `type: RealTime` to work around a failure: `RealTime` is Data Cloud-backed and returns `INVALID_API_INPUT "To set Type to RealTime, make sure that dataSourceType is set to ContextDefinition."` — a different source model this DT does not need. If a `LowVolume`/`SingleSobject` create returns `INVALID_CROSS_REFERENCE_KEY`, treat it as a **body/reference** problem (confirm `dataSpaceName='default'` resolves and that `sourceObject` + every `parameters[].fieldName` exist on the object), not an org-provisioning blocker.

6. **Re-read to verify — never trust the write's own echo.** Toggles echo the written value; gate on the INDEPENDENT read-back (the `verify-*` step), which confirms the preference actually persisted. Where a route is irreversible or org-scoped, only fire after explicit confirmation and a read that shows it is genuinely off.

7. **Person Accounts enablement is a readiness-gated 3-write chain — prefer the PROPOSED Aura wizard route over the implemented Connect endpoint.** `GET /headless/invoke/platform/person-account-settings` returns four gates (`termsConditionsAccepted`, `accountRecordTypeCreated`, `profilePermsSet`, `orgWideSharingSet`) + `allStepsComplete`. Enable is IRREVERSIBLE — fire only on explicit authorization.

## Runtime validation (end-to-end proof the setup works)

Once Act 1 (and the internal-creation surfaces) are in place, these native Connect APIs prove the pipeline end-to-end. They are `implemented` (real Connect endpoints). Each sits behind a runtime gate (below), so treat them as diagnostics of the org's runtime readiness, not proof-of-success steps.

| # | Step id | Purpose | Controller / API | Route |
|---|---|---|---|---|
| 40 | `create-referral-runtime` | validate | Connect `postReferralManagement` (`ReferralManagementInputRepresentation`) | POST `/services/data/v67.0/connect/health/referral-management/referrals` (implemented) |
| 41 | `create-guest-referral-runtime` | validate | Connect `postGuestReferral` (guest intake) | `POST /connect/health/referral-management/guest-referrals` — guest-only + UiTier-excluded (HTTP 404 for external callers; authenticated POST → "This API can only be called by Guest"), so **no served/dispatchable route** — GAP; exercise only via the published guest form |

- **`create-referral-runtime`** validates the internal path: with the app enabled (Act 1 steps 5a/5b) and Person Accounts present, POST a referral and confirm a `ClinicalServiceRequest` is created. The runtime is gated at the **user** level even with the org-level Referral Management app ON: an unentitled user gets 403 `FUNCTIONALITY_NOT_ENABLED`. The `captchaToken` requirement is the SECOND gate: `postGuestReferral`'s input representation requires a **mandatory `captchaToken`** field (a Google reCAPTCHA response token, `ReCaptcha` type, ~2-minute TTL) produced only when a real user solves the reCAPTCHA widget on the published guest form. **Net: this endpoint is NOT smoke-testable from any authenticated/programmatic session** — (1) the session is not a Guest user, and (2) no valid `captchaToken` can be synthesized. Verify it ONLY by submitting through the published guest referral form as an actual guest (a human solves the reCAPTCHA → a live token is minted and posted; requires the Experience site published Live — see Act 6). The captcha gate is the whole point of `enable-captcha-verification` (step 32) + the site-key/OmniScript captcha fields (steps 34/36).
