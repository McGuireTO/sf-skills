**Setting up Health Cloud from a new org means running all four acts in order — Act 1 (foundation), Act 2 (data protection & account config), Act 3 (Person Accounts, record types, layouts, profiles), and Act 4 (Patient Card & Timeline) — NOT just the foundation toggles.** This is the full end-to-end setup for a brand-new org: the ordered, resumable journey that ties together the individual Setup pages an admin would otherwise navigate by hand. Finishing Act 1 is not finishing the setup.

Guide an admin through standing up **Health Cloud** in a **brand-new org** — Console, FHIR Data Model, Discovery Framework, data protection, accounts, Person Accounts, record types, layouts, and the Patient Card + Timeline — in the **strict order** the underlying preferences and platform features require, with a validate-only stance on anything genuinely external to Salesforce (edition, license, paid add-on entitlements).

This skill automates as much of the setup as a real customer-org admin can legitimately do via API/metadata: license/prereq detection, org-preference toggles, Settings/RecordType/Profile/FlexiPage metadata deploys, and the Person Accounts + Timeline enablement sequences. It does **not** assume internal-only enablement paths — everything here is something a customer admin could trigger themselves, just faster and in the right order.

## Orient the admin first — what this skill is (and is not)

Before you confirm scope or run anything, give the admin a one-screen orientation so expectations are set up front. Do this proactively — don't wait to be asked.

- **This is the ordered, end-to-end setup *workflow*, not a single toggle.** It walks the org through four stages in the exact order the platform requires: (1) **foundation** — Health Cloud Console, FHIR / Clinical Data Model, Discovery Framework, OmniStudio, and the advanced capabilities (Einstein for Health Cloud, Disease Surveillance, Data Cloud, Context Service, Digital Experiences, and the care org preferences — Enhanced Care Plans, Integrated Care Management, Care Gap); (2) **data protection & account configuration** — Consent Management, Translation Workbench, Contacts to Multiple Accounts; (3) **Person Accounts** — record types, page layouts, profile visibilities; (4) **Patient Card + Timeline** on the org-default patient record page, then **create + activate the Health Cloud Console app's own record page** (last, once its component prerequisites are all on). State these four stages to the admin before your first write (see the *Mandatory pre-write plan* below).
- **Be explicit about what is automated vs. what stays manual.** Almost every step is something a customer admin can do themselves via API/metadata — org-preference toggles, Settings/RecordType/Profile/FlexiPage deploys, and the Person Accounts + Timeline sequences — this skill just does them faster and in the correct order. A few surfaces have **no dispatchable API** (they are called out inline as gaps): for those, surface the manual Setup-UI path, mark that step INCOMPLETE, and keep going — never fabricate a call. External prerequisites (edition, license, paid add-on entitlements) are **validate-only** — the skill checks them and redirects if unmet; it never tries to grant them.
- **This is NOT the one-click "enable everything" button — do not shortcut through the bulk orchestrator.** Do **not** call the bulk `executeHealthCloudBasicFeatureSetup` orchestrator (or any single "basic feature setup" / one-shot enable-all entry point) as a fast path. That orchestrator ignores its argument, force-enables *every* feature in its internal map, and silently kicks off the **IRREVERSIBLE Person Accounts automation the admin never confirmed** — exactly the destructive side effect this ordered workflow exists to prevent. Enable each feature through its own dedicated control (the per-step routes in the Acts below), and gate the two irreversible steps on explicit confirmation. If the admin explicitly asks for "the one-click setup" or "just turn everything on," explain why this skill deliberately does not do that and walk them through the ordered flow instead.
- **This is a setup workflow, not a test plan or an audit checklist.** Actually run and verify each step against the live org (re-read state, gate on independent read-backs) — do not merely narrate what "should" happen or produce a checklist of expected outcomes.

## Scope & definition of done — READ THIS FIRST

**"Set up Health Cloud" / "Configure Health Cloud" / "Prepare my org for Health Cloud" with no narrowing qualifier means run ALL FOUR ACTS, in order: Act 1 → Act 2 → Act 3 → Act 4.** Act 1 (foundation) is only *one* of the four acts. If you find yourself about to stop after the foundation toggles for an unqualified "set up Health Cloud" request, that is the bug this section exists to prevent — keep going through Act 4.

**You are NOT done after Act 1 (or Act 3).** The setup is complete only when **Act 4's end state** is reached (Patient Card placed where possible; Timeline enabled, configured, and activated). If a specific, documented gate blocks a later step, **report that gate explicitly and still run every step that is not blocked** — never silently stop. A run that ends after the foundation toggles is a *partial* run, not a completed setup; say so plainly if you must stop early.

**This targets a brand-new org.** If Service Cloud is already configured (shared Case/Account/Contact objects), STOP — that is a separate migration path, not this workflow (precondition `OrgState.NoExistingServiceCloudConfig`). Act 1's `detect-service-cloud-presence` step is the observable check that surfaces this: it queries for a Service Cloud footprint and warns about the shared Case/Account/Contact objects before any write; the precondition is the hard backstop.

**Two irreversible gates dominate the flow.** Enabling **Person Accounts** (Act 3) CANNOT be undone and is a hard prerequisite for record types, layouts, and components. The org-level **Timeline toggle** (Act 4) is a second one-way gate — it cannot be turned back off. Both require explicit user confirmation before you dispatch them. If the admin declines Person Accounts, END the workflow — every remaining step depends on it.

**`enable-data-protection` (Consent Management) is REQUIRED for HIPAA.** If the admin skips it, mark the final summary INCOMPLETE.

**Deferred / gapped steps are NOT stop signals.** Steps that hit a declared gap (no dispatchable API for a Setup surface) are called out so you set correct expectations — **not** so you halt the act sequence. Surface the manual Setup path, mark that step INCOMPLETE, and continue with everything not blocked. Never fabricate a call for a gapped step. **Note the exception: the advanced-capability entitlements (Einstein for Health Cloud, Disease Surveillance, Data Cloud, Context Service) are NOT gaps and are NOT skippable — they are EXPECTED on a properly provisioned Health Cloud org, so a genuinely absent one is a BLOCKING error (see the advanced-capabilities section below), not a deferral.**

## Decision points (confirm before Act 1 writes; drive optional steps)

This workflow has one admin decision (layout strategy). Confirm it up front; it gates which layout steps run. ### 1. Layout strategy — default `custom-layouts`

> Create custom role-specific Patient and Provider page layouts (recommended), or reuse the default Person Account layout for both record types?

- **`custom-layouts` (default):** Create a Patient layout and a Provider layout with role-specific fields, then map the Patient/Provider record types to them. Runs `create-patient-layout` + `create-provider-layout` + `assign-person-account-layouts-to-profiles` (the assignment is its own Profile `<layoutAssignments>` PUT, not part of the RT create).
- **`default-layout`:** Keep the auto-generated Person Account layout for both record types. **Skips** `create-patient-layout`, `create-provider-layout`, and `assign-person-account-layouts-to-profiles`; the record types map to the default Person Account layout instead.

(This is distinct from the idempotency skip on `enable-data-cloud`, which correctly skips when Data Cloud is ALREADY provisioned — an is-it-already-done check, unrelated to entitlement.)

## Transport & deploy discipline (applies to EVERY Act — read before your first write)

These rules are cross-cutting; each Act references them rather than repeating them.

1. **Prefer the platform dispatch tool; two transports exist.** Most toggles are dispatcher-backed Aura routes (`/headless/invoke/...`) or Connect APIs (`/services/data/...`). All **metadata** (Settings singletons, RecordType, Profile, FlexiPage, CustomObject) deploys through the headless Metadata REST resource **`/services/data/vXX/headless/metadata`** (`POST`=create, `PUT`=update, `GET`=read; `{type, fullName, xmlRep}`) — supported end-to-end for every metadata type this skill touches. Each step below names its transport. Prefer the headless Metadata resource for Settings/RecordType/Profile/CustomObject and for creating/activating FlexiPage pages built from standard `force:*` components. **The FlexiPage binds of the Patient Card and timeline (`healthcloud:patientCard`, `industries_common:timeline`, Act 4 steps 49 & 55) ALSO go through the headless `PUT` — one `dispatch` call, `PUT /services/data/vXX/headless/metadata` with the flat body `{type:"FlexiPage", fullName:"<DeveloperName>", xmlRep:"<whole re-authored page>"}`.** NO multipart, NO zip, NO `sf` CLI — a single JSON PUT `dispatch` issues directly. ⚠ The ONE load-bearing rule: **send the WHOLE page.** FlexiPage `<flexiPageRegions>` are ordered full-record lists, so the PUT is a FULL REPLACE (not the component-level merge that Settings/Profiles/CustomObject actionOverrides get) — a PUT that omits pre-existing components drops them. So read-modify-write: GET the current `xmlRep`, insert your `<itemInstances>`, PUT the whole page preserving every existing region/component. The Patient Card is the standard **`healthcloud:patientCard`** component, bound by `<componentName>` with **NO `<componentInstanceProperties>` block** (this is how Lightning App Builder persists it). The timeline is **`industries_common:timeline`** and MUST be bound WITH a **`timelineConfigs`** component property naming the 4 OOTB Timeline Configurations (`String[]`, each element a `TimelineObjectDefinition` DeveloperName: `HC_Clinical_Data`, `HC_Engagement_Data`, `HC_Patients_Life_Story`, `HC_Assessments`) — a property-free timeline bind does NOT auto-resolve the org's active configs, so the timeline renders none/wrong configurations. Two gotchas, both TRANSACTIONAL (the whole PUT fails atomically): (1) **component access** — a bind before the backing feature is enabled fails `hasComponentAccess` (run `handle-timeline-toggle` before the timeline; Health Cloud enablement in Act 1 provides `healthcloud:patientCard`); (2) **property shape** — the timeline's `timelineConfigs` is array-typed, so serialize it as a `<valueList>` of `<valueListItems><value>…</value></valueListItems>` (one per config); an EMPTY `timelineConfigs` property (name, no value) rolls back the whole page and a SCALAR `<value>` is rejected with `FIELD_CUSTOM_VALIDATION_EXCEPTION: "Value is not allowed for Array attribute type in API version 49 and above."`. ALWAYS gate on an independent read-back, never the write echo.
2. **Headless-metadata merge semantics (know these before deploying).** The headless Metadata resource does **component-level MERGE** for **Settings singletons and Profiles** (a single-field deploy preserves every other field), so the `read-*` snapshot steps are OPTIONAL for those. **FlexiPage region-adds are read-modify-write** (region item lists are ordered — read the whole page, add your `<itemInstances><componentInstance>` — the v68.0 shape, not a bare `<componentInstances>` — PUT the whole page back), and **CustomObject `actionOverrides` also merge** (non-destructive). If `/headless/metadata` genuinely 404s on a stripped org, that is an org route artifact, not a missing capability — fall back to the **manual Setup UI** and Tooling SOQL reads; never conclude "the capability is missing" from a dispatcher 404 alone.
3. **What MERGES vs what is read-modify-write (know before deploying).** Everything in THIS rule goes through `/headless/metadata` (no CLI) — INCLUDING the two OmniStudio/industries FlexiPage binds, which use the same whole-page `dispatch` PUT of rule 1 (`PUT /headless/metadata {type:FlexiPage, fullName, xmlRep:<whole page>}`). **Settings singletons MERGE** (`PUT Account` with only `<enableRelateContactToMultipleAccounts>true>` preserves every other AccountSettings field; same for `LanguageSettings`). **Profiles MERGE at the component level too** — a `PUT type=Profile` carrying ONLY the target `<recordTypeVisibilities>` blocks assigns RT visibility WITHOUT wiping other perms (`PermissionsModifyAllData` on the System Administrator profile stays true). So NEVER round-trip the ~1MB full Profile; send the minimal fragment. **CustomObject `actionOverrides` also MERGE** (activating a record page is a one-override PUT; every pre-existing override survives). **FlexiPage region-adds are READ-MODIFY-WRITE, not merge** — region item lists are ordered, so read the whole page's `xmlRep`, add your `<itemInstances><componentInstance>` (distinct `<identifier>`; the v68.0 shape — NOT a bare `<componentInstances>`), and write the whole page back preserving every existing region/component. That write-back is a `/headless/metadata` PUT for ALL pages — `force:*`-only pages AND the two OmniStudio/industries binds (steps 49 & 55) alike; the only rule is send the WHOLE page (a partial-page PUT drops the components you omit). **RecordType create** is a `POST` whose `xmlRep` is a `<CustomObject>` root wrapping a nested `<recordTypes>` block (a top-level `<RecordType>` is rejected). Because Settings/Profile/CustomObject all merge, the `read-*` snapshot steps are OPTIONAL for them (useful only for read-back verification); the FlexiPage `read-*` step IS required (it feeds the RMW).
4. **Re-read to verify — never trust the write's own echo.** Toggles echo the written value; gate on an INDEPENDENT read-back (the `verify-*` / `get-*` step), which confirms the preference actually persisted. Metadata deploys: gate on `state=Changed` plus a follow-up retrieve.
5. **Ground the final report in fresh queries**, not stale session notes — re-query end state immediately before reporting "done."
6. **CLI TLS handling:** if a `sf` command needs relaxed TLS for a local/dev endpoint, set `NODE_TLS_REJECT_UNAUTHORIZED=0` **inline on that single command only** — NEVER in shell init, a profile, or Claude settings.

**Act 1 — foundation notes (ordering & findings):**

- **`validate-hc-license` is the gate for the whole workflow.** The check returns `true` when reachable; on a denied caller it throws rather than returning `false` — treat any error as "not provisioned, HALT." ## Metadata write discipline (recap)

`assign-person-account-record-type-to-profiles`, `create-*-record-type`, `read/add-patient-flexipage`, `create/activate-account-flexipage`, and the AccountSettings/LanguageSettings/CommunitiesSettings writes touch Metadata via the headless Metadata REST resource (`/services/data/vXX/headless/metadata`) — no CLI needed for these. Merge semantics: **Settings singletons, Profiles, and CustomObject `actionOverrides` MERGE at the component level** — send the MINIMAL fragment (a single-field Settings PUT, a minimal `<recordTypeVisibilities>` Profile PUT, a one-override CustomObject PUT); never round-trip the whole record. Creating/activating a `force:*`-only FlexiPage works through this headless resource. **The two OmniStudio/industries binds on the org-default page (`add-patient-card-to-flexipage`, `add-timeline-to-flexipage`) ALSO go through it — one `dispatch` `PUT /services/data/vXX/headless/metadata {type:FlexiPage, fullName, xmlRep:<whole page>}` each; NO multipart, NO zip, NO `sf` CLI.** The Health Cloud Console app's OWN record page is instead **created whole** (not bound-into): `create-console-flexipage` POSTs the full `Account_Record_Page` (a CHILD of `healthcloud__HealthCloudAccount_rec_L_3Col` — its `<parentFlexiPage>` and `<template>` are part of the encoded shape) via the same headless resource, then `activate-console-flexipage-as-app-default` sets it as the app's App Default with a `View`-actionOverride `CustomApplication` PUT on `standard__HealthCloudConsole` — and ⚠ unlike CustomObject actionOverrides, **`CustomApplication` is a FULL-RECORD REPLACE, not a merge**: read-modify-write the whole app (a minimal one-override PUT 400s `FIELD_INTEGRITY_EXCEPTION "…supported only for Lightning apps"` because it drops `<uiType>Lightning</uiType>`), preserving `<uiType>`/`<navType>`/`<tabs>`/`<formFactors>`/`<workspaceConfig>`. Unlike Settings/Profile/CustomObject, **FlexiPage regions do NOT merge** — `<flexiPageRegions>` are ordered full-record lists, so the PUT is a FULL REPLACE: re-author the WHOLE `.flexipage` (carry every existing region/component; on a standalone region never add `<mode>`), and a partial-page PUT drops every omitted component. The PUT is ATOMIC, so its real gotchas are component access (enable the backing feature first — Health Cloud enablement for `healthcloud:patientCard`, `handle-timeline-toggle` for the timeline) and property shape: bind the Patient Card by `<componentName>` with NO `<componentInstanceProperties>` block, but bind the timeline WITH a `timelineConfigs` property naming the 4 OOTB configs, serialized as a `<valueList>` (an empty or scalar `timelineConfigs` fails the timeline PUT). **BOTH binds MUST carry a `<visibilityRule>` of `{!Record.IsPersonAccount}` EQUAL true** (child order: `<componentInstanceProperties>`* → `<componentName>` → `<identifier>` → `<visibilityRule>`) — the activated page is the org-default Account page shared by all 4 record types, so without the rule the Patient Card and Timeline leak onto Business accounts. Gate on read-back (asserting the `<visibilityRule>` persisted), never the write echo. **RecordType create** wraps a nested `<recordTypes>` block in a `<CustomObject>` root (a top-level `<RecordType>` is rejected). **Layout create/modify** is the one Metadata-shaped write that does NOT go through `/headless/metadata` (that path 400s "Invalid fullName" for `Layout`) — use the native **Tooling `Layout` sObject** REST instead (`POST`/`PATCH /services/data/vXX/tooling/sobjects/Layout`), targeting the `PersonAccount` entity (`FullName: PersonAccount-<Name> Layout`) for person layouts; a plain Tooling REST call. If `/headless/metadata` 404s on a stripped org, fall back to Tooling SOQL reads + the manual Setup UI. **`IndustriesSettings` (`enable-group-membership`)** writes through this same headless resource — a `type=IndustriesSettings` PUT of the minimal `<enableGroupMembershipPref>` fragment (a true→false→true round-trip each returns `200 success:true`, GET-confirmed) is the primary write channel here too; an **MDAPI file-based deploy** of the Industries settings is only a stripped-org fallback.
