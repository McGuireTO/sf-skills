# Home Health — Agentforce Setup

Child skill extracted from `home-health-guided-setup` Phase 13 (`[enablement toggles + layout + perms automate; agent build + subagent + data library are headlessly automatable on a Data-Cloud-provisioned org; only Voice steps are blocked by org provisioning and a narrow prompt-action publish-500]`) · gated by `HealthCloud.orgHasHomeHealthAgentWithoutGenAI` — only run this phase once real Agentforce/Einstein agents are in scope for the customer.

**CANONICAL EXECUTION SEQUENCE for this phase (follow in this order):**

1. **Enable the settings first.** Run **Step 0** (the four `Einstein Generative AI` platform toggles) — it turns on the Agentforce platform itself and is the prerequisite for everything downstream; check `EinsteinGptSettings.enableEinsteinGptPlatform` state from Phase 0 first (if already on from an earlier phase, Step 0 is idempotent). Then run **Step 1** (`EnableAgentPref`, the HC-specific `healthCloudGenAIPref`). These are the enablement toggles — do them before any agent authoring.
2. **Create the default agent.** Step 0's toggles #3/#4 (`AgentPlatformSettings.enableAgentPlatform` + `EinsteinCopilotSettings.enableEinsteinGptCopilot`) activate the built-in **Agentforce (Default) Agent** — the org's `Copilot_for_Salesforce` `BotDefinition` (`Type=InternalCopilot`) flips its `BotVersion.Status` to `Active`. Confirm it is Active (`SELECT Status FROM BotVersion WHERE BotDefinitionId=<the InternalCopilot BotDefinition Id>` → `Active`) before building the HH agent.
3. **Create the Home Health agent with its subagent.** Run **Step 4** — build the HH agent + its `PatientHomeHealthcareMgmt` subagent end-to-end and automatically. It depends ONLY on Step 0's toggles, NOT on steps 1–3 (SCV/contact-center, which are org-provisioning-gated) and NOT on Data Cloud (that gates only step 5's library grounding). Do not defer Step 4 to manual just because the SCV/Bot-legal-terms paths are blocked; those are separate dependency chains.
4. **Check Data Cloud enablement.** Data Cloud is required ONLY if the customer wants to set up a data library (Step 5) to ground the agent — it is NOT needed for anything above. Probe provisioning via the data-library prerequisites check / the Data-Cloud-enabled check (see Step 5).
   - **If Data Cloud is NOT enabled →** do NOT block or fail silently on the whole phase. **Prompt the user** that Data Cloud must be enabled/provisioned in order to set up the data library, then **continue to the next phase (or any other pending steps in this phase — e.g. steps 6/7)** without the library. An empty `rag_feature_config_id` is the correct end state on a non-Data-Cloud org; the agent built in step 3 is already fully active without it.
   - **If Data Cloud IS enabled →** proceed to **Step 5** and **ask the user, in interaction mode, how to set up the data library** — which library grounds which agent (create a new library vs attach an existing one, its name/source). Do not fabricate the library or its grounding target.

Do NOT include it in the required enablement set, and do NOT block Step 0 or Step 4 if it can't be turned on.** Deploy the three required toggles in this order (each `Succeeded`, each re-retrieved to confirm persistence):

   | # | Setup UI toggle | Settings type · field → value | Notes |
   |---|---|---|---|
   | 1 | Einstein Generative AI Platform | `EinsteinGptSettings.enableEinsteinGptPlatform = true` | master switch — **must be first** (the one hard-proven ordering dependency) |
   | opt | Agents/Bots runtime | `BotSettings.enableBots = true` | ⚠️ **NOT A PREREQUISITE — skip it for the default (Employee/`InternalCopilot`) agent.** Only needed if you deliberately build the optional *service/messaging* variant (`EinsteinServiceAgent`, patient-facing Messaging/voice, bound to the Messaging channel).    ✅ **THE PUBLISH GATE IS THE AGENT *TYPE*, NOT `enableBots` (holds end-to-end with `enableBots=false`).** An Agentforce agent's root record is a `BotDefinition`, but its **`Type`** depends on the `.agent` `config.agent_type`. Build it as an **Employee agent** and it publishes + activates freely with Bots off:
   ```text
   config:
       agent_label: "Home Health Agent"
       agent_template: "EmployeeCopilot__AgentforceEmployeeAgent"
       developer_name: "Home_Health_Agent_Emp"
       agent_type: "AgentforceEmployeeAgent"
   model_config:
       model: "model://sfdc_ai__DefaultGPT54"
   ```
   → produces a `BotDefinition` with `Type=InternalCopilot`, which is **not** legal-terms-gated. **If you OMIT `agent_type`, or leave a `messages:` (welcome/error) block or `@MessagingSession.*` linked variables in the blueprint, it compiles to an `EinsteinServiceAgent`** (patient-facing Messaging/voice agent) — and *that* type is what (a) validation-errors `INVALID_API_INPUT "Default agent user is required for the agent type EinsteinServiceAgent"` and (b) requires `enableBots=true` + the one-time Einstein Bots legal-terms acceptance because it binds to the Messaging channel. So: for the default HH agent build, use the Employee `agent_type` above and DROP the `messages:` block and all messaging linked vars (the voice-call subagent `PatientHomeHlthcrMgmtVoiceCall` is out of scope and is never built) — then publish/activate need no Bot legal terms. Only build the `EinsteinServiceAgent` variant (and accept the legal-terms hand-off) if a patient-facing Messaging/voice channel agent is explicitly wanted.

   **Recipe — create bundle → assemble afscript → patch draft → publish → activate:**
   1. `POST /nextgen-authoring/bundles` with a flat body `{"label":"Home Health Agent","apiName":"Home_Health_Agent"}` → 201, returning `{bundleId, id:<draftVersionId>, apiName:"Home_Health_Agent_1", versionStatus:"DRAFT", ...}` (server auto-suffixes `apiName` on collision — don't pass `agentTemplate`, it 400s `JSON_PARSER_ERROR "Unrecognized field"`).
   2.    3. `PATCH /nextgen-authoring/bundle-versions/{draftId}` with body `{"assets":[{"resourceName":"definition.agent","resourceType":"agentDefinition","resourceContent":"<full afscript string>"}]}` → 204.    5. `POST /nextgen-authoring/bundle-versions/{draftId}/activate` → 204.

   🚨 **MECHANISM CHOICE — prefer the org-domain REST recipe above; the `sf agent` CLI publish routes through an EXTERNAL gateway that 404s on orgs not registered on it (typically scratch / pre-release / internal dev orgs).** `sf agent publish authoring-bundle` bootstraps a JWT and POSTs the compiled bundle to the **external Agentforce SFAP gateway** (`api.salesforce.com/einstein/ai-agent/authoring`, with `test.api.`/`dev.api.` fallbacks). On an org not registered on that public gateway, all three hosts return **404 `AgentApiNotFound`** and **nothing is written to the org** (`BotDefinition` count stays 0) — a failure that looks like "the agent couldn't be created" but is really just the wrong endpoint. Reserve the CLI publish for orgs known to be registered on the SFAP gateway. **Do not conclude "agent build failed" from a `sf agent publish` 404 without first trying the org-domain REST path.**
