# Home Health — Install Field Service Managed Package

Leaf skill extracted from `home-health-guided-setup` Phase 0 step 4 (the FSL package install), so it can be delegated to from any phase/skill that needs FSL present — not just re-derived inline each time. `home-health-guided-setup-enable-org-fsl` delegates to this skill rather than inlining the detect/install/poll/fallback logic.

## Guided hand-off contract (applies if every automated path below fails)

Many steps in the Home Health family have no API (managed-package install being the canonical example) — these are **guided manual hand-offs**, not dead ends:

1. **Guide, don't just name it.** Present: (a) what it accomplishes and why it's needed, (b) the exact org-specific link, (c) numbered click-by-click instructions, (d) the public help-doc link.
2. **State what's blocked behind it.** Tell the caller which later steps can't complete until this lands, and which steps can keep running in parallel meanwhile.
3. **Wait for the "done" signal**, then **verify, don't trust** — re-run the detect query. If it still fails, say exactly what you looked for and found, and keep waiting.
4. **On verified success, resume automatically** — don't make the caller re-issue the ask.

**Prerequisite polling.** After handing off manual instructions, re-check the prerequisite on each subsequent turn (treat any response during the wait as a possible "is it ready?"). When it flips to satisfied, announce it ("✅ Field Service package detected — resuming setup") and return control. Do not poll on a timer or fabricate a "still waiting" status.

## Install procedure

**Field Service package install — try the direct package-install API first, then the manual Salesforce Go hand-off if it can't run on this org; ALWAYS surface this proactively.** (wizard step `InstallFieldServicePackage`, `action.type: Manual` in the wizard, but a direct API install path is now proven — see below.) This is a hard gate: run its detection early and, if unmet, attempt the direct API install then ASK the admin (with the resolved Salesforce Go link) only if it can't install on this org; do not assume they know to.

- **Detect first (this is what tells you whether to act):** query installed packages via **Tooling API** — `GET /services/data/vXX/tooling/query?q=SELECT SubscriberPackage.Name, SubscriberPackage.NamespacePrefix FROM InstalledSubscriberPackage`. FSL present = a package with namespace `FSL` (or name containing "Field Service"). A quick corroborating check: `SELECT COUNT() FROM FSL__Scheduling_Policy__c` — a `400 sObject type 'FSL__…' is not supported` means the package is NOT installed. (Note: `InstalledSubscriberPackage` is a **Tooling** object — a Data-API `/query` against it 400s.)

- **Tier orchestration — SEQUENTIAL, never parallel; `IN_PROGRESS` is NOT failure.** FSL install is a long process (commonly 20–30 min). Run the tiers strictly in order and stop at the first one that is accepted:
  1. Try PRIMARY. If it reports `IN_PROGRESS` (request accepted, not yet done) → **STOP: do NOT also fire SECONDARY** (avoids a double install). Keep polling PRIMARY and return `in-progress` to the caller so it can use the wait productively (see Return contract).
  2. Only if PRIMARY **errors explicitly** (`Package Not Found`, create 400, or `Status=ERROR`) → try SECONDARY. If SECONDARY is accepted (`201` and status `IN_PROGRESS`) → same: stop, keep polling, return `in-progress`.
  3. Only if BOTH explicitly error → TERTIARY (Salesforce Go hand-off).
  - Status meanings: `IN_PROGRESS` = running, keep polling (even if it looks frozen); `SUCCESS`/`ENABLED` = candidate success, **confirm only via the `FSL` namespace in the detect query**; `ERROR`/`NOT_ENABLED` with the namespace still absent = that tier failed.
  - **Overall polling ceiling ≈ 45 min** from the first accepted install. If `FSL` is still absent after that, treat the in-flight tier as failed and move to the next tier / Salesforce Go. While a tier is `IN_PROGRESS`, poll opportunistically (callers re-check at safe points, see the parent's "while FSL installs" rule) — don't block foreground on it.
  - During the Salesforce Go manual hand-off keep polling the detect query too; the admin finishing the install flips the state to `installed` without needing a message.

- **PRIMARY: install the FSL managed package directly via the Tooling API `PackageInstallRequest` — token-only, no browser, no admin interaction.** This is the same mechanism Salesforce's own managed-package install flow uses; it just needs a bearer token. Three sub-steps:
  - **(i) Resolve the latest compatible FSL version id** from the public Salesforce Sites endpoint (no auth): `GET https://d36000000z1fneac.my.salesforce-sites.com/PublicLatestFSL` → take `response.trim().substring(0,15)` (or the full trimmed body — the API accepts the 15- or 18-char id) → the `04t…` `SubscriberPackageVersion` id. This host is the **hardcoded production endpoint** (a fixed platform endpoint, not an org setting), not an org-specific value — it always publishes the current prod-GA FSL version. (The response is a bare `04t…` id; it rotates each FSL release, which is exactly why you fetch it at runtime rather than hardcoding one.)
  - **(ii) Confirm the org can resolve that version** before attempting the install: `GET /tooling/query?q=SELECT Id,Name,MajorVersion,MinorVersion FROM SubscriberPackageVersion WHERE Id='<04t>'`. A 200 with the record (its `Name` + version, e.g. a named seasonal release) = go; a **`Package Not Found`** error = this org's instance does not have that FSL version published/replicated (see the prod-versioning caveat below) → **skip straight to the headless recipe / manual fallback**, do not attempt the create (it will only 400).
  - **(iii) Create the install request** (Tooling REST, **omit** the internal `PackageInstallSource` field — it's a SOAP-only enum core sets internally and is not required over REST): `POST /services/data/vXX/tooling/sobjects/PackageInstallRequest` body `{"SubscriberPackageVersionKey":"<04t>","SecurityType":"Full","NameConflictResolution":"Block"}` → `{"id":"0Hf…","success":true}`. Then **poll** `GET /tooling/sobjects/PackageInstallRequest/<id>` reading `Status` (+ `Errors`): `IN_PROGRESS` → keep polling (~20–30 s cadence; FSL takes ~4–15 min), until `SUCCESS` or `ERROR`. On `SUCCESS`, **re-run the detect query** to confirm the `FSL` namespace now appears (authoritative signal — same rule as the recipe path). On `ERROR`, surface `Errors` and fall through.
  - ⚠️ **Prod-versioning caveat (this is the crux of why the API install "fails" on some orgs).** The `04t` from the endpoint is a **prod-GA** version id; it only resolves on instances where FSL is actually published (real **production / sandbox / test instances**). On a **scratch / pre-release** org, step (ii) returns `Package Not Found` and step (iii) 400s `INVALID_CROSS_REFERENCE_KEY "invalid cross reference id"` — **not a broken call, just an org where the version isn't available.** So the resolve-check in (ii) is the gate: if it fails, this path is unavailable on this org — fall through to the Salesforce Go manual hand-off, don't retry the create.

- **SECONDARY (executed) — the headless Setup Discovery recipe.** When the direct `PackageInstallRequest` can't run on this org (step (ii) `Package Not Found`, or the create/poll errors), **attempt this recipe next — before falling back to the browser.** It installs the FSL managed package headlessly along with the other quickstart steps (org settings, perm sets, console app, profiles). It is environment-gated and does **not** always converge (it can run `IN_PROGRESS → NOT_ENABLED` without installing — see the ⚠️ warning below), which is exactly why it sits *second*, behind `PackageInstallRequest`, and why success is judged solely by the `FSL`-namespace detect query, never by a status flip. The executed order is **`PackageInstallRequest` (primary) → Setup Discovery recipe (secondary) → manual Salesforce Go (tertiary/final)**. Fire the recipe (`POST` → `201 {"success":true}`, status → `IN_PROGRESS`):
  - `POST /services/data/vXX/connect/setup/discovery/feature/field-service-initial-cloud-setup/enable` with body `{}` — triggers the `fieldServiceQuickstart` recipe (min-version 254). Requires View Setup + Customize Application (System Administrator covers it).
  - Poll `GET /services/data/vXX/connect/setup/discovery/feature/field-service-initial-cloud-setup/status` until `status` leaves `IN_PROGRESS`. `ENABLED` (and FSL now present via the detect query) = success; re-run the detect query to confirm the `FSL` namespace actually appears before treating it as done.
  - ⚠️ **Do NOT trust `status` alone — the ONLY authoritative success signal is the `FSL` namespace appearing in the package-detect query.** The recipe is **environment-gated**: on orgs where the FSL `04t` package version isn't available or Field Service isn't licensed, it returns to `NOT_ENABLED` **without** installing. **A clean/empty status body is NOT proof of success** — for example, on an org without Field Service licensing, the recipe can run `IN_PROGRESS → NOT_ENABLED` and leave a *completely clean* status body (`enableBlockedReasons: []`, `dependencyStatuses: []`, `blockedByApexLock: false`) yet installed **no** package; `enableBlockedReasons`/`dependencyStatuses` sometimes surface why (e.g. `ANOTHER_FEATURE_RUNNING` if a prior run is still in flight — re-fire once it clears), but often they're empty even on a no-op.
  - ⏱️ **Convergence takes real time — a frozen `IN_PROGRESS` is NOT itself failure.** Confirmed on a live orgfarm/pc-rnd test instance: the recipe can sit at `IN_PROGRESS` with `lastStatusUpdate` apparently frozen for **20–30 minutes** before either converging (namespace appears) or genuinely going `NOT_ENABLED`. **Do not conclude "headless path unavailable" before at least 20–30 minutes have elapsed since the fire.** Poll on a ~1–2 min cadence (don't busy-loop) and keep polling through that window — a few minutes of apparent staleness is normal, not a signal. Only once 20–30 min have passed with the `FSL` namespace still absent (whether `status` reads `IN_PROGRESS` or has flipped to `NOT_ENABLED`) should you treat it as "headless path unavailable on this org" and fall through to the manual hand-off. If other non-FSL-dependent setup work is available, keep making progress on that in parallel rather than blocking the whole session on this wait — do not loop indefinitely once the window has elapsed, and never report success on a `status` flip or an empty status body alone.

- **TERTIARY / FINAL FALLBACK (executed only after BOTH API paths above have failed): the manual Salesforce Go hand-off.** If the direct `PackageInstallRequest` can't run on this org (step (ii) `Package Not Found`, or the create/poll errors) **AND** the Setup Discovery recipe also fails to converge (still no `FSL` namespace **after waiting out the full 20–30 min convergence window** per the ⏱️ note above — don't fall back early just because `status` looks stuck), **hand the admin the org-specific Salesforce Go link and wait** (say this, don't wait to be asked). Both API paths (primary + secondary) are gated on the org's instance having the FSL version published/replicated, so when neither resolves on this org, browser install is the remaining route.
  - 🔴 **MANDATORY — resolve and render the ACTUAL clickable URL; never emit the angle-bracket placeholder and never skip the link.** So **compute it**: take the org's live instance URL (from the session / `sf org display`), replace the `.my.salesforce.com` host suffix with `.my.salesforce-setup.com`, and append `/lightning/setup/page/feature/industries-health-cloud-home-health/home?topic=SalesforceGo`. Present the finished `https://…` URL as a clickable link in the message. **Build it from the connected org — never hardcode a domain.** The transform (generic, using `<mydomain>` only as a stand-in for whatever host the connected org actually has): `https://<mydomain>.my.salesforce.com` → `https://<mydomain>.my.salesforce-setup.com/lightning/setup/page/feature/industries-health-cloud-home-health/home?topic=SalesforceGo`. Read `<mydomain>` from the live session's instance URL at runtime; do not carry any specific org's domain in this skill. (If the instance host doesn't end in `.my.salesforce.com` — e.g. a sandbox `.sandbox.my.salesforce.com` — apply the same `→ .my.salesforce-setup.com`-family substitution for that host form; the point is a real, resolved, clickable link built from the current org, not a placeholder and not a fixed domain.)
  > "Home Health depends on the **Field Service managed package**, and it isn't installed on your org yet. I tried installing it directly through the API, but this org's instance doesn't have the current FSL package version available to install that way — so the remaining route is the browser. Please install it here (this is the Salesforce Go guided-setup page for your org, which resolves the current package version automatically):
  > **`https://<yourdomain>.my.salesforce-setup.com/lightning/setup/page/feature/industries-health-cloud-home-health/home?topic=SalesforceGo`** ← *render the org's real resolved URL here per the MANDATORY note above, not this template*
  > (Alternative: Setup → **Field Service Settings** → toggle Field Service on → **Get Managed Package**; or the AppExchange listing. Background doc: https://sfdc.co/HomeHealthInstallFieldService.) Let me know once it's installed and I'll verify and continue. Meanwhile I can set up everything that doesn't depend on the package."

- **Do NOT fabricate an `apvId`.** The old `…/packagingSetupUI/ipLanding.app?apvId=<version-id>` pattern needs a version Id that **rotates every FSL release** — inventing one risks a stale/wrong version and violates the no-invented-setup-data rule. The Salesforce Go page above (and the Field Service Settings toggle) resolve the current version for the admin, so prefer those.

- **After the admin confirms**, verify via the Tooling query above (namespace `FSL` now present) before reporting success back to the caller.

## Return contract (for callers delegating to this skill)

Report back one of: `installed` (namespace `FSL` confirmed present, state which path — primary/secondary/manual — got it there), `in-progress` (primary or secondary accepted the install and it has not finished; state which tier and the request id / recipe; caller should START Phase 13 (`home-health-guided-setup-agentforce-setup`) now and re-check this skill at safe points — this is NOT a failure), or `awaiting-manual` (both automated tiers failed or the ~45-min ceiling elapsed; Salesforce Go hand-off issued; caller should keep running Phase 13 / non-FSL-dependent work and re-poll this skill — detect-query polling continues during the manual install).
